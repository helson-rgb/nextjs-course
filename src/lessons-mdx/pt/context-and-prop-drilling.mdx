# Hooks Customizados, useReducer e Context

Esta lição é o capstone do capítulo de Fundamentos de React. Hooks customizados, `useReducer` e Context são as três ferramentas que te permitem domar a complexidade à medida que uma app React cresce: extrair lógica repetida, modelar transições de estado de forma explícita, e partilhar dados sem passar props por cada nível da árvore.

## Extrair lógica em hooks customizados

Um hook customizado é uma função JavaScript cujo nome começa com `use` e que chama pelo menos um outro hook dentro de si. Só isso — sem API especial, sem registo. Escreves-o, chamas-o, o React trata-o como qualquer outra chamada de hook.

```jsx
// useToggle — estado booleano com uma função flip estável
import { useState, useCallback } from 'react';

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);
  return [on, toggle];
}

// Utilização — comportamento de estado idêntico, sem boilerplate
const [menuAberto, toggleMenu] = useToggle();
const [isDark, toggleDark] = useToggle();
```

Cada componente que chama `useToggle` obtém o seu próprio estado independente — os hooks não são instâncias partilhadas. O valor de extrair é reutilizar a *lógica*, não partilhar o *estado*.

### useLocalStorage

Persistir estado no `localStorage` requer um inicializador que lê do storage, e um effect que escreve de volta. Extrai isso uma vez:

```jsx
import { useState, useEffect } from 'react';

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    // inicializador lazy — corre uma vez no mount
    try {
      const stored = window.localStorage.getItem(key);
      return stored !== null ? JSON.parse(stored) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {}
  }, [key, value]);

  return [value, setValue];
}
```

Substituto direto de `useState`:

```jsx
// Antes
const [tema, setTema] = useState('light');

// Depois — persiste entre recarregamentos de página
const [tema, setTema] = useLocalStorage('tema', 'light');
```

### useDebounce

Inputs de pesquisa que fazem um pedido de rede em cada tecla são dispendiosos. `useDebounce` atrasa a atualização de um valor até o utilizador pausar:

```jsx
import { useState, useEffect } from 'react';

export function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancela se o valor mudar antes do delay
  }, [value, delay]);

  return debounced;
}

// Utilização
const query = useDebounce(inputValue, 400); // só atualiza após pausa de 400ms
useEffect(() => {
  if (query) fetchResultados(query);
}, [query]);
```

A função de limpeza cancela o timeout pendente em cada tecla — apenas o último, depois de o utilizador parar de escrever, dispara.

### Regras dentro de hooks customizados

Os hooks customizados seguem as mesmas regras que os hooks normais: chama-os ao nível de topo, nunca dentro de condicionais ou loops. Como os hooks customizados chamam hooks dentro deles, a garantia de ordem de chamada do React aplica-se a tudo o que está dentro deles.

## Quando useReducer supera useState

`useReducer` aceita uma função reducer e um estado inicial, devolve o estado atual e uma função `dispatch`:

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
dispatch({ type: 'ADICIONAR', payload: novoItem });
```

O reducer é uma função pura: `(estadoAtual, action) => novoEstado`. Vive fora do componente, aceita qualquer objeto de action e devolve um novo estado.

**Usa `useReducer` quando:**

- Várias chamadas `useState` sempre atualizam em conjunto (um formulário com 5 campos).
- O próximo estado depende de condições complexas em múltiplos campos existentes.
- Queres testar transições de estado de forma isolada — o reducer é uma função simples, facilmente testável unitariamente.
- O mesmo estado é modificado por muitos eventos diferentes, e queres um único sítio para ver todas as transições.

Compara a mesma lista de tarefas expressa de duas formas:

```jsx
// useState — disperso, difícil de ver todas as transições de uma vez
const [tarefas, setTarefas] = useState([]);
function adicionarTarefa(texto)  { setTarefas(prev => [...prev, { id: Date.now(), texto, feito: false }]); }
function alternarTarefa(id)      { setTarefas(prev => prev.map(t => t.id === id ? {...t, feito: !t.feito} : t)); }
function removerTarefa(id)       { setTarefas(prev => prev.filter(t => t.id !== id)); }
function limparFeitas()          { setTarefas(prev => prev.filter(t => !t.feito)); }
```

```jsx
// useReducer — todas as transições num só lugar, nomeadas e explícitas
function tarefasReducer(state, action) {
  switch (action.type) {
    case 'adicionar':
      return [...state, { id: Date.now(), texto: action.texto, feito: false }];
    case 'alternar':
      return state.map(t => t.id === action.id ? { ...t, feito: !t.feito } : t);
    case 'remover':
      return state.filter(t => t.id !== action.id);
    case 'limpar_feitas':
      return state.filter(t => !t.feito);
    default:
      throw new Error('Action desconhecida: ' + action.type);
  }
}

const [tarefas, dispatch] = useReducer(tarefasReducer, []);
dispatch({ type: 'adicionar', texto: 'Comprar leite' });
dispatch({ type: 'alternar', id: 3 });
```

O `default: throw` é intencional — actions desconhecidas são erros do programador, não condições de runtime.

## Context: estado partilhado sem prop drilling

O prop drilling — passar o mesmo valor através de 4 componentes intermediários que não o usam — é um sinal de que o context pode ajudar:

```jsx
// Passar tema por cada camada
<App tema={tema}>
  <Layout tema={tema}>
    <Sidebar tema={tema}>
      <Button tema={tema} /> {/* finalmente usado aqui */}
    </Sidebar>
  </Layout>
</App>
```

O Context fornece um valor em qualquer ponto da árvore e torna-o disponível a qualquer descendente que o peça — sem props:

```jsx
import { createContext, useContext, useState } from 'react';

// 1. Cria o context — null é o sentinel para "provider em falta"
const ThemeContext = createContext(null);

// 2. O provider é dono do estado e distribui-o
export function ThemeProvider({ children }) {
  const [tema, setTema] = useState('light');
  return (
    <ThemeContext.Provider value={{ tema, setTema }}>
      {children}
    </ThemeContext.Provider>
  );
}

// 3. Um hook customizado valida o context e expõe uma API limpa
export function useTema() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTema deve ser usado dentro de <ThemeProvider>');
  return ctx;
}
```

Qualquer componente dentro de `<ThemeProvider>` pode chamar `useTema()` — não importa a profundidade:

```jsx
function Button() {
  const { tema } = useTema(); // lê do context
  return <button className={'btn btn--' + tema}>Clica</button>;
}
```

<Callout type="warn">
**O Context volta a renderizar todos os consumidores em cada mudança de valor.** Quando o estado do `ThemeProvider` atualiza, o React volta a renderizar *todos* os componentes que chamaram `useContext(ThemeContext)` — mesmo que só usem um campo que não mudou. Isto é adequado para dados que mudam lentamente (tema, locale, utilizador atual). É a ferramenta errada para estado de alta frequência (posição, offset de scroll, um ticker em tempo real) — usa uma biblioteca de estado dedicada como Zustand ou Jotai para esses casos.

O Context é um *mecanismo de distribuição*, não uma biblioteca de gestão de estado. Resolve o prop drilling; não substitui o Redux.
</Callout>

**Quando o context é a ferramenta certa:**
- Locale / idioma da app (muda no máximo uma vez por sessão).
- Tema (claro / escuro).
- Utilizador autenticado (muda apenas no login/logout).
- Definições globais da app que raramente atualizam.

**Quando não é:**
- Estado partilhado por apenas 2–3 componentes adjacentes — eleva o estado para o pai comum mais próximo.
- Dados derivados que atualizam frequentemente — a composição de componentes com `children` muitas vezes resolve o prop drilling sem nenhum context.

## Conclusões principais

<Callout type="tip">
**Um hook customizado é apenas uma função que chama hooks.** Chama-lhe `use*`, extrai o estado + effects + lógica do teu componente, devolve o que o chamador precisa. Cada componente que chama o hook obtém o seu próprio estado independente.

**`useLocalStorage` é `useState` com persistência.** O inicializador lazy lê do storage uma vez; o effect escreve de volta em cada mudança. É um substituto direto: `const [x, setX] = useLocalStorage('chave', padrão)`.

**`useReducer` centraliza todas as transições.** Quando um componente tem muitas formas de atualizar o mesmo estado, coloca-as num reducer. O reducer é puro, testável e legível — cada transição é visível numa instrução `switch`.

**O Context distribui; não gere.** Usa-o para valores partilhados que mudam lentamente (tema, locale, utilizador). Cada mudança de valor de context volta a renderizar todos os consumidores — mantém os valores de context estáveis e prefere dividir os contexts por frequência de atualização.

**Envolve sempre `useContext` num hook customizado com null guard.** `if (!ctx) throw new Error(...)` apanha componentes acidentalmente renderizados fora do seu provider — um erro de runtime é muito mais fácil de depurar do que um `undefined` silencioso.
</Callout>
