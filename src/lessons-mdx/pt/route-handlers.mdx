# Route Handlers

Route Handlers são arquivos `route.js` que expõem endpoints HTTP a partir do seu app Next.js. Eles utilizam as APIs padrão da Web `Request` e `Response` — sem Express, sem `req`/`res`, sem adaptadores de framework. Exporte uma função com o nome do método HTTP e o Next.js encaminha as requisições para ela.

## A convenção do arquivo `route.js`

Coloque um arquivo `route.js` dentro de `app/` no caminho que deseja servir. O arquivo **não** pode ficar junto de um `page.js` no mesmo segmento — um segmento pode ser uma página ou um endpoint de API, nunca os dois.

```
app/
├── api/
│   └── notes/
│       ├── route.js        ← /api/notes  (GET, POST)
│       └── [id]/
│           └── route.js    ← /api/notes/42  (GET, DELETE)
└── page.js                 ← a página inicial (segmento separado)
```

Cada método HTTP que você deseja suportar é uma exportação nomeada:

```js
// src/app/api/notes/route.js
export async function GET(request) { ... }
export async function POST(request) { ... }
```

Nomes de métodos suportados: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.

## Request e Response — padrões Web

Route Handlers recebem um [`Request`](https://developer.mozilla.org/en-US/docs/Web/API/Request) padrão e devem retornar um [`Response`](https://developer.mozilla.org/en-US/docs/Web/API/Response). Use `Response.json()` para o caso mais comum:

```js
export async function GET() {
  const data = { message: 'Hello' };
  return Response.json(data);                    // 200 OK, Content-Type: application/json
}

export async function POST(request) {
  const body = await request.json();             // parse JSON body
  return Response.json(body, { status: 201 });   // 201 Created
}
```

Para respostas que não são JSON, use o construtor `Response` diretamente:

```js
return new Response('plain text', {
  status: 200,
  headers: { 'Content-Type': 'text/plain' },
});
```

204 No Content (comum para DELETE) envia uma resposta sem corpo:

```js
return new Response(null, { status: 204 });
```

## Lendo a requisição

### Corpo JSON

```js
export async function POST(request) {
  const { title, body } = await request.json();
  // ...
}
```

### Parâmetros de query

```js
export async function GET(request) {
  const { searchParams } = new URL(request.url);
  const limit = Number(searchParams.get('limit') ?? 10);
  // ...
}
```

### Headers

```js
export async function POST(request) {
  const token = request.headers.get('Authorization');
  if (!token) return Response.json({ error: 'Unauthorized' }, { status: 401 });
  // ...
}
```

## Segmentos de rota dinâmicos

Segmentos dinâmicos funcionam da mesma forma que em rotas de página. O segundo argumento do handler é um objeto de contexto; `params` é uma **promise** no Next.js 16 e deve ser aguardado com `await`:

```js
// src/app/api/notes/[id]/route.js
export async function DELETE(request, { params }) {
  const { id } = await params;   // ← sempre use await em params
  await deleteNote(Number(id));
  return new Response(null, { status: 204 });
}
```

## Definindo headers e cookies com `NextResponse`

O `Response` padrão resolve a maioria dos casos. Quando você precisa definir cookies ou redirecionar, importe `NextResponse` de `next/server`:

```js
import { NextResponse } from 'next/server';

export async function GET(request) {
  const data = await fetchData();
  const response = NextResponse.json(data);
  response.cookies.set('last-visit', new Date().toISOString(), {
    httpOnly: true,
    maxAge: 60 * 60 * 24,
  });
  return response;
}
```

`NextResponse.redirect()` e `NextResponse.rewrite()` são os outros usos mais comuns — os mesmos helpers que você pode reconhecer do middleware.

## `NextRequest` — requisição estendida

`NextRequest` (de `next/server`) estende o `Request` padrão com alguns extras:

```js
import { NextRequest } from 'next/server';

export async function GET(request) {
  // request.nextUrl é uma URL já parseada — sem necessidade de `new URL(request.url)`
  const limit = request.nextUrl.searchParams.get('limit');

  // request.cookies lê e escreve cookies
  const token = request.cookies.get('auth-token')?.value;
  // ...
}
```

Para handlers simples que apenas leem `request.json()`, `request.headers` ou `request.url`, use o `Request` padrão — sem import necessário. Recorra ao `NextRequest` quando precisar de `.nextUrl`, `.cookies` ou `.geo`.

## Route Handlers vs Server Actions

<Callout type="warn">
**Use a ferramenta certa para cada situação.**

| Cenário | Use |
|---|---|
| API REST pública consumida por apps mobile, serviços de terceiros ou `curl` | Route Handler |
| Endpoint de webhook recebendo POST do Stripe, GitHub etc. | Route Handler |
| Envio de formulário que muta dados dentro do seu próprio app Next.js | Server Action |
| Busca de dados para uma página | Async Server Component — nenhum handler necessário |

Server Actions rodam no contexto de um render completo do Next.js — podem chamar `revalidatePath`, `redirect` e acessar módulos exclusivos do servidor diretamente. Route Handlers são endpoints HTTP sem estado, sem conhecimento do render atual. Quando o cliente é o seu próprio formulário Next.js, Server Actions são mais simples. Quando o cliente é qualquer coisa externa, Route Handlers são a escolha certa.
</Callout>

## A API — Notes

O app do curso expõe o mesmo `notes-store.js` usado pelas Server Actions como uma API REST em `/api/notes`. Um cliente externo (um app mobile, um script cURL, outro serviço) pode ler e escrever notas por meio dessa API enquanto a página `/playground/notes` continua usando Server Actions internamente.

```
GET    /api/notes          → 200  [{ id, body }, ...]
GET    /api/notes?limit=2  → 200  primeiras 2 notas
POST   /api/notes          → 201  { id, body }
GET    /api/notes/1        → 200  { id, body }
DELETE /api/notes/1        → 204  (sem corpo)
```

```js
// src/app/api/notes/route.js
import { getNotes, addNote } from '@/lib/notes-store';

export async function GET(request) {
  const { searchParams } = new URL(request.url);
  const limit = searchParams.has('limit') ? Number(searchParams.get('limit')) : undefined;
  const notes = limit ? getNotes().slice(0, limit) : getNotes();
  return Response.json(notes);
}

export async function POST(request) {
  const body = await request.json();
  const text = body?.body?.toString().trim();
  if (!text) return Response.json({ error: '"body" field is required' }, { status: 400 });
  const note = addNote(text);
  return Response.json(note, { status: 201 });
}
```

```js
// src/app/api/notes/[id]/route.js
import { getNotes, removeNote } from '@/lib/notes-store';

export async function DELETE(request, { params }) {
  const { id } = await params;
  const exists = getNotes().some((n) => n.id === Number(id));
  if (!exists) return Response.json({ error: 'Not found' }, { status: 404 });
  removeNote(Number(id));
  return new Response(null, { status: 204 });
}
```

<Callout type="info">
**Teste com `curl`.** Com o servidor de desenvolvimento rodando na porta 3000:

```bash
# Listar todas as notas
curl http://localhost:3000/api/notes

# Adicionar uma nota
curl -X POST http://localhost:3000/api/notes \
  -H "Content-Type: application/json" \
  -d '{"body":"Added from curl"}'

# Deletar a nota 1
curl -X DELETE http://localhost:3000/api/notes/1

# Verificar se foi removida
curl http://localhost:3000/api/notes
```

Depois acesse `/playground/notes` — a deleção feita via `curl` aparece refletida na UI alimentada por Server Actions. Eles compartilham o mesmo store em memória.
</Callout>

## Playground — fetch no cliente vs fetch no servidor

Em [Padrões de Busca de Dados](/lessons/data-fetching-patterns) você buscou dados de um async Server Component — a requisição rodou no servidor e o navegador recebeu o HTML pronto. O componente abaixo faz o mesmo fetch no **navegador** usando `useEffect`. As duas abordagens conversam com a mesma API; a diferença está em _onde_ a requisição é executada e o que o navegador recebe.

```
Abordagem com Server Component (Lição 11):
  Servidor busca → envia HTML pronto → navegador renderiza, zero JS enviado

Abordagem com Client Component (este playground):
  Navegador renderiza esqueleto → JS carrega → fetch executa → estado atualiza → re-render
```

Alterne entre as duas abas e compare: a abordagem do servidor não mostra estado de carregamento no painel de rede; a abordagem do cliente mostra um frame em branco/esqueleto seguido pela atualização dos dados.

## Principais conclusões

<Callout type="tip">
**Route Handlers são arquivos `route.js` com exportações nomeadas de métodos HTTP.** `export async function GET` trata requisições GET; `export async function POST` trata requisições POST. Sem adaptador de framework — `Request` e `Response` padrão da Web.

**`Response.json(data, { status })` é o recurso mais usado.** Para `204 No Content`, use `new Response(null, { status: 204 })`. Para redirecionamentos ou definição de cookies, recorra ao `NextResponse`.

**Segmentos dinâmicos usam `await params`.** O segundo argumento é `{ params }` — uma promise no Next.js 16. Sempre use `await` antes de desestruturar.

**Route Handlers e Server Actions compartilham o mesmo processo.** Podem importar os mesmos módulos, ler as mesmas variáveis de ambiente e acessar o mesmo banco de dados. A diferença está no chamador: clientes HTTP externos usam Route Handlers; seus próprios formulários Next.js usam Server Actions.

**Não crie um Route Handler apenas para ler dados de uma página.** Async Server Components buscam diretamente — nenhum endpoint é necessário. Route Handlers fazem sentido quando o consumidor está fora do seu app Next.js.
</Callout>
