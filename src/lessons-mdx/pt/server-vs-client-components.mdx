# Server vs Client Components

Esta é a mudança conceptual mais importante no App Router do Next.js. Cada componente que escreves é um Server Component ou um Client Component, e essa distinção muda onde corre, o que pode fazer e quanto JavaScript é enviado para o browser.

## Os componentes são Server por defeito

No App Router, todos os componentes são Server Components a menos que digas o contrário. Os Server Components correm no servidor durante o pedido (ou no momento da build para páginas estáticas). Renderizam para HTML e um formato serializado ligeiro chamado RSC Payload — **nenhum JavaScript deles é alguma vez enviado para o browser**.

```jsx
// src/app/page.js — Server Component (não precisa de directiva)
export default async function HomePage() {
  const data = await fetch('https://api.example.com/stats');  // corre no servidor
  const stats = await data.json();
  return <h1>Total de utilizadores: {stats.count}</h1>;
}
```

O `async/await` aqui não é um truque — é uma função assíncrona standard. O servidor aguarda a sua conclusão antes de enviar HTML para o cliente.

## A directiva 'use client'

`'use client'` é um literal de string no topo de um ficheiro. Diz ao Next.js (e ao React) que este ficheiro — e todos os componentes importados a partir dele — corre no browser:

```jsx
'use client';

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

`'use client'` define uma **fronteira**, não um marcador "apenas este ficheiro". Tudo o que for importado abaixo dela — componentes, utilitários, pacotes de terceiros — passa a fazer parte do bundle do cliente. A fronteira propaga-se para baixo através da árvore de importações.

<Callout type="warn">
`'use client'` não significa "este componente apenas corre no browser." Significa "este ficheiro é a raiz de uma sub-árvore de cliente." Qualquer componente importado dentro de um ficheiro `'use client'` é também um Client Component, mesmo que não tenha a directiva.
</Callout>

## O que corre onde

As capacidades de cada ambiente são fundamentalmente diferentes:

| Capacidade | Server Component | Client Component |
|---|---|---|
| `async/await` ao nível de topo | ✅ | ❌ (usa `useEffect`) |
| Acesso directo a base de dados / sistema de ficheiros | ✅ | ❌ |
| Usar segredos de ambiente (`process.env`) | ✅ | ❌ (exposto ao browser) |
| `useState`, `useReducer` | ❌ | ✅ |
| `useEffect`, `useRef` | ❌ | ✅ |
| APIs do browser (`window`, `document`, `localStorage`) | ❌ | ✅ |
| Event handlers (`onClick`, `onChange`) | ❌ | ✅ |
| Envia JavaScript para o browser | ❌ (nenhum) | ✅ |

O benefício de zero JS é real. Uma página com uma listagem de produtos, um artigo em markdown ou um gráfico de dashboard que nunca precisa de interactividade pode renderizar como HTML puro. O utilizador não descarrega nenhum código de componente React para isso — First Contentful Paint mais rápido, bundle menor, hidratação mais barata.

## O padrão de intercalação

Um Client Component não pode importar um Server Component — fazê-lo puxaria código exclusivo do servidor para o bundle do cliente. Mas um Server Component pode passar outro Server Component para um Client Component através da prop `children`:

```jsx
// ✅ Padrão: servidor passa servidor como children para cliente
// src/app/page.js (server)
import { ThemeProvider } from '@/components/ThemeProvider'; // 'use client'
import { Article } from '@/components/Article';             // server

export default function Page() {
  return (
    <ThemeProvider>
      <Article />   {/* renderizado pelo servidor, passado como children pré-renderizados */}
    </ThemeProvider>
  );
}
```

`ThemeProvider` recebe `children` como um RSC Payload já renderizado — nunca importa `Article` directamente, por isso `Article` permanece no servidor.

## Árvore de decisão

```
Preciso de onClick, onChange ou algum event handler?
  → Client Component

Preciso de useState, useReducer ou useContext?
  → Client Component

Preciso de useEffect ou useRef?
  → Client Component

Preciso de APIs do browser (window, document, localStorage)?
  → Client Component

Caso contrário:
  → Server Component (obter dados, aceder à BD, usar segredos)
```

Em caso de dúvida, começa com um Server Component. Adiciona `'use client'` apenas quando deparas com um dos bloqueadores acima. Mantém a fronteira o mais fundo possível na árvore para maximizar a porção renderizada no servidor, com zero JS.

## Playground 1 — Fetch no servidor → filtro no cliente

O server component obtém uma lista de posts a partir de um endpoint JSON e passa-os como prop para um client component que trata do input de filtro. A lógica de filtro requer `useState`, por isso tem de ser um Client Component — mas a obtenção de dados permanece no servidor.

<Playground
  template="nextjs"
  files={{
    'app/page.js': `import { PostList } from './PostList';

async function getPosts() {
  const res = await fetch('https://jsonplaceholder.typicode.com/posts?_limit=10');
  return res.json();
}

export default async function Page() {
  const posts = await getPosts();
  return (
    <div style={{ fontFamily: 'sans-serif', padding: '2rem', maxWidth: '600px' }}>
      <h1 style={{ fontSize: '1.5rem', fontWeight: 700, marginBottom: '1.5rem' }}>Posts</h1>
      {/* Pass server-fetched data to client component */}
      <PostList posts={posts} />
    </div>
  );
}`,
    'app/PostList.js': `'use client';

import { useState } from 'react';

export function PostList({ posts }) {
  const [query, setQuery] = useState('');
  const filtered = posts.filter(p =>
    p.title.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Filter posts…"
        style={{
          width: '100%', padding: '0.5rem 0.75rem',
          border: '1px solid #e2e8f0', borderRadius: '6px',
          fontSize: '0.875rem', fontFamily: 'sans-serif',
          marginBottom: '1rem', boxSizing: 'border-box',
        }}
      />
      {filtered.length === 0 && (
        <p style={{ color: '#94a3b8', fontSize: '0.875rem' }}>No posts match.</p>
      )}
      <ul style={{ listStyle: 'none', padding: 0, margin: 0, display: 'flex', flexDirection: 'column', gap: '0.5rem' }}>
        {filtered.map(post => (
          <li key={post.id} style={{
            padding: '0.625rem 0.875rem',
            border: '1px solid #e2e8f0',
            borderRadius: '6px',
            fontSize: '0.875rem',
          }}>
            <span style={{ color: '#94a3b8', marginRight: '0.5rem', fontSize: '0.75rem' }}>#{post.id}</span>
            {post.title}
          </li>
        ))}
      </ul>
    </div>
  );
}`,
  }}

  height={480}

## Playground 3 — Server component como children de um cliente

`ThemeProvider` é um Client Component que gere um tema claro/escuro. `Article` é um Server Component (sem directiva) que lê dados. O truque: `Page` é também um server component e passa `<Article />` como children para `ThemeProvider` — `Article` nunca acaba no bundle do cliente.

## Pontos-chave

<Callout type="tip">
**Servidor por defeito — adiciona `'use client'` apenas quando precisares.** Cada componente começa como Server Component. Adiciona a directiva apenas quando deparas com um bloqueador concreto: estado, efeitos, APIs do browser ou event handlers.

**`'use client'` é uma fronteira, não uma opção por ficheiro.** Tudo o que for importado abaixo da fronteira passa a fazer parte do bundle do cliente — incluindo pacotes de terceiros. Mantém a fronteira o mais fundo possível na árvore.

**Server Components não enviam JS.** Uma página cheia de Server Components renderiza para HTML sem nenhum código React para esses componentes no bundle. Isto melhora directamente o tempo de carregamento e o FCP.

**Usa o padrão children para manter servidores numa árvore de cliente.** Um Client Component não pode importar um Server Component, mas pode receber um como `children` ou como prop. O Server Component é pré-renderizado no servidor e o Client Component nunca o importa.

**Árvore de decisão: event handlers / estado / efeitos / APIs do browser → cliente. Tudo o resto → servidor.**
</Callout>
