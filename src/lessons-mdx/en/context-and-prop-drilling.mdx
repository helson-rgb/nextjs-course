# Custom Hooks, useReducer & Context

This lesson is the capstone of the React Fundamentals chapter. Custom hooks, `useReducer`, and Context are the three tools that let you tame complexity as a React app grows: extract repeated logic, model state transitions explicitly, and share data without threading props through every level of the tree.

## Extracting logic into custom hooks

A custom hook is a JavaScript function whose name starts with `use` and that calls at least one other hook inside it. That's it — no special API, no registration. You write it, you call it, React treats it like any other hook call.

```jsx
// useToggle — boolean state with a stable flip function
import { useState, useCallback } from 'react';

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);
  return [on, toggle];
}

// Usage — identical state behaviour, zero boilerplate
const [menuOpen, toggleMenu] = useToggle();
const [isDark, toggleDark] = useToggle();
```

Each component that calls `useToggle` gets its own independent state — hooks are not shared instances. The value of extraction is reusing the *logic*, not sharing the *state*.

### useLocalStorage

Persisting state to `localStorage` requires an initialiser that reads from storage, and an effect that writes back. Extract that once:

```jsx
import { useState, useEffect } from 'react';

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    // lazy initialiser — runs once on mount
    try {
      const stored = window.localStorage.getItem(key);
      return stored !== null ? JSON.parse(stored) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {}
  }, [key, value]);

  return [value, setValue];
}
```

Drop-in replacement for `useState`:

```jsx
// Before
const [theme, setTheme] = useState('light');

// After — persists across page loads
const [theme, setTheme] = useLocalStorage('theme', 'light');
```

### useDebounce

Search inputs that fire a network request on every keystroke are wasteful. `useDebounce` delays updating a value until the user pauses:

```jsx
import { useState, useEffect } from 'react';

export function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cancel if value changes before delay
  }, [value, delay]);

  return debounced;
}

// Usage
const query = useDebounce(inputValue, 400); // only updates after 400ms pause
useEffect(() => {
  if (query) fetchResults(query);
}, [query]);
```

The cleanup function cancels the pending timeout on every keystroke — only the final one, after the user stops typing, fires.

### Rules inside custom hooks

Custom hooks follow the same rules as regular hooks: call them at the top level, never inside conditions or loops. Because custom hooks call hooks themselves, React's call-order guarantee applies to everything inside them.

## When useReducer beats useState

`useReducer` takes a reducer function and an initial state, returns the current state and a `dispatch` function:

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
dispatch({ type: 'ADD', payload: newItem });
```

The reducer is a pure function: `(currentState, action) => nextState`. It lives outside the component, accepts any action object, and returns a new state.

**Reach for `useReducer` when:**

- Several `useState` calls always update together (a form with 5 fields).
- The next state depends on complex conditions across multiple existing fields.
- You want to test state transitions in isolation — the reducer is a plain function, easily unit-tested.
- The same state is modified by many different events, and you want a single place to see all transitions.

Compare the same todo list expressed two ways:

```jsx
// useState — scattered, hard to see all transitions at once
const [todos, setTodos] = useState([]);
const [filter, setFilter] = useState('all');

function addTodo(text)  { setTodos(prev => [...prev, { id: Date.now(), text, done: false }]); }
function toggleTodo(id) { setTodos(prev => prev.map(t => t.id === id ? {...t, done: !t.done} : t)); }
function removeTodo(id) { setTodos(prev => prev.filter(t => t.id !== id)); }
function clearDone()    { setTodos(prev => prev.filter(t => !t.done)); }
```

```jsx
// useReducer — all transitions in one place, named and explicit
function todosReducer(state, action) {
  switch (action.type) {
    case 'add':
      return [...state, { id: Date.now(), text: action.text, done: false }];
    case 'toggle':
      return state.map(t => t.id === action.id ? { ...t, done: !t.done } : t);
    case 'remove':
      return state.filter(t => t.id !== action.id);
    case 'clear_done':
      return state.filter(t => !t.done);
    default:
      throw new Error('Unknown action: ' + action.type);
  }
}

const [todos, dispatch] = useReducer(todosReducer, []);
dispatch({ type: 'add', text: 'Buy milk' });
dispatch({ type: 'toggle', id: 3 });
```

The `default: throw` is intentional — unknown actions are programmer errors, not runtime conditions.

## Context: shared state without prop drilling

Prop drilling — passing the same value through 4 intermediate components that don't use it — is a sign that context might help:

```jsx
// Drilling theme through every layer
<App theme={theme}>
  <Layout theme={theme}>
    <Sidebar theme={theme}>
      <Button theme={theme} /> {/* finally used here */}
    </Sidebar>
  </Layout>
</App>
```

Context provides a value at any point in the tree and makes it available to any descendant that asks — without props:

```jsx
import { createContext, useContext, useState } from 'react';

// 1. Create the context — null is the sentinel for "missing provider"
const ThemeContext = createContext(null);

// 2. The provider owns the state and distributes it
export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

// 3. A custom hook validates the context and exposes a clean API
export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used inside <ThemeProvider>');
  return ctx;
}
```

Any component inside `<ThemeProvider>` can call `useTheme()` — no matter how deep:

```jsx
function Button() {
  const { theme } = useTheme(); // reads from context
  return <button className={'btn btn--' + theme}>Click</button>;
}
```

<Callout type="warn">
**Context re-renders every consumer on every value change.** When the `ThemeProvider`'s state updates, React re-renders *every* component that called `useContext(ThemeContext)` — even if it only uses a field that didn't change. This is fine for slowly changing data (theme, locale, current user). It is the wrong tool for high-frequency state (position, scroll offset, a real-time ticker) — use a dedicated state library like Zustand or Jotai for those.

Context is a *distribution mechanism*, not a state management library. It solves prop drilling; it doesn't replace Redux.
</Callout>

**When context is the right tool:**
- App locale / language (changes at most once per session).
- Theme (light / dark).
- Authenticated user (changes on login/logout only).
- App-wide settings that rarely update.

**When it is not:**
- State shared by just 2–3 adjacent components — lift state to their nearest common parent instead.
- Frequently updating derived data — component composition with `children` often solves prop drilling without any context at all.

## Key takeaways

<Callout type="tip">
**A custom hook is just a function that calls hooks.** Name it `use*`, extract the state + effects + logic from your component, return whatever the caller needs. Each component that calls the hook gets its own independent state.

**`useLocalStorage` is `useState` with persistence.** The lazy initialiser reads from storage once; the effect writes back on every change. It is a drop-in replacement: `const [x, setX] = useLocalStorage('key', default)`.

**`useReducer` centralises all transitions.** When a component has many ways to update the same state, pull them into a reducer. The reducer is pure, testable, and readable — every transition is visible in one `switch` statement.

**Context distributes; it does not manage.** Use it for slowly changing shared values (theme, locale, user). Every context value change re-renders all consumers — keep context values stable and prefer splitting contexts by update frequency.

**Always wrap `useContext` in a custom hook with a null guard.** `if (!ctx) throw new Error(...)` catches components accidentally rendered outside their provider — a runtime error is far easier to debug than a silent `undefined`.
</Callout>
