# State & Events

State is how React remembers things between renders. Every interactive UI — a counter, a form, a toggle — is driven by state.

## What state is

A regular JavaScript variable resets on every render. React calls your component function again whenever it needs to update the screen; any `let` declaration starts fresh each time:

```jsx
// ❌ Never works — count resets to 0 on every render
function Counter() {
  let count = 0;
  return (
    <button onClick={() => { count += 1; console.log(count); }}>
      Count: {count}
    </button>
  );
}
```

The button click fires, `count` reaches 1, but the screen never changes — React doesn't know anything happened. State is the fix: React stores it *outside* your function and hands the current value back on every render:

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Count: {count}
    </button>
  );
}
```

Calling `setCount` tells React "re-render this component". React calls your function again — and this time passes back the new value of `count`.

## Declaring state with useState

```jsx
const [value, setValue] = useState(initialValue);
```

- `value` — the current state snapshot for this render.
- `setValue` — call this to schedule a re-render with a new value.
- `initialValue` — used only on the first render; can be a number, string, object, array, or `null`.

**Two rules for hooks:**
- Call `useState` (and all hooks) **at the top level** of your component — never inside `if`, loops, or nested functions.
- Call hooks only inside React function components or custom hooks.

React identifies each piece of state by the order in which `useState` is called. Changing that order across renders breaks the match between calls and stored values.

## State updates are asynchronous

Calling a setter does not update the variable immediately. React schedules a re-render and the new value is only visible in the *next* render. The current render's value is fixed — it's a constant:

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // ⚠️ Still 0 — the render hasn't happened yet
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}
```

<Callout type="warn">
`console.log(count)` right after `setCount` always prints the **old value**. `count` is a constant bound at the start of this render — nothing can change it mid-function. The updated value only appears once React re-renders and your function runs again.

This also means calling `setCount(count + 1)` multiple times in the same handler only increments once — each call reads the same stale snapshot:

```jsx
// ❌ count starts at 0 — all three calls read 0, result is 1
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
```

Use the functional updater form to chain multiple updates correctly.
</Callout>

## The functional updater form

When the next value depends on the previous one, pass a function instead of a value:

```jsx
setCount(prev => prev + 1);
```

React queues these functions and applies them in order, each receiving the result of the previous one:

```jsx
// ✅ Each updater receives the latest prev — result is 3
setCount(prev => prev + 1);
setCount(prev => prev + 1);
setCount(prev => prev + 1);
```

Use the functional form whenever:
- You call the setter multiple times in one handler.
- The new state depends on the current state.
- You're inside a `setTimeout`, `fetch` callback, or any async function where the captured `value` may be stale.

## Event handlers

React attaches a synthetic event object to every handler. The most common patterns:

```jsx
// onClick — fires on click
<button onClick={(e) => console.log(e.currentTarget)}>Click</button>

// onChange — fires on every keystroke
<input onChange={(e) => setText(e.target.value)} />

// onSubmit — fires on form submission
<form onSubmit={(e) => { e.preventDefault(); submit(); }}>
  ...
</form>
```

**`e.preventDefault()`** stops the browser's default action. For forms this prevents a page navigation; for links it prevents following the href. Call it first, before any state updates.

Define handlers as named functions when the logic spans more than one line — it keeps JSX readable and makes the function easy to test:

```jsx
function handleChange(e) {
  const trimmed = e.target.value.trimStart();
  setText(trimmed);
}

return <input onChange={handleChange} />;
```

Pass the function *reference*, not a call: `onChange={handleChange}`, not `onChange={handleChange()}`. The second form runs immediately on every render.

## Never mutate state directly

React detects changes by reference equality. Mutating an existing object or array does not create a new reference — React sees the same value and skips the re-render:

```jsx
// ❌ Mutation — React sees the same object, no re-render
const next = state;
next.count += 1;
setState(next);

// ✅ New object — React sees a different reference, triggers re-render
setState({ ...state, count: state.count + 1 });
```

### Immutable update patterns

**Object — update one field:**
```jsx
setState(prev => ({ ...prev, name: 'Alice' }));
```

**Array — add an item:**
```jsx
setItems(prev => [...prev, newItem]);
```

**Array — remove an item:**
```jsx
setItems(prev => prev.filter(item => item.id !== targetId));
```

**Array — update one item:**
```jsx
setItems(prev =>
  prev.map(item => item.id === targetId ? { ...item, done: true } : item)
);
```

The pattern is always: spread or derive a *new* value — never modify the one React already holds.

## Key takeaways

<Callout type="tip">
**State is memory outside the function.** Local variables reset on every render; state persists. React stores it, your component reads it, and calling the setter schedules the next render.

**State updates are snapshots, not mutations.** Each render captures its own value of every state variable. Calling a setter schedules a re-render — the current value never changes mid-render. `console.log(value)` after a setter always shows the old snapshot.

**Use the functional updater when new state depends on old state.** `setX(prev => ...)` is the correct form when calling the setter multiple times in one handler, in async code, or anywhere you can't guarantee the captured value is fresh.

**Never mutate objects or arrays in state.** Always produce a new value: spread objects, spread arrays to add, `filter` to remove, `map` to update. Mutation bypasses React's change detection and leaves the UI out of sync.

**`e.preventDefault()` first.** For form submits and link clicks, call it before any state updates to stop the browser's default navigation.
</Callout>
