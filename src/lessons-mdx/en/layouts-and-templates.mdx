# Layouts & Templates

A layout wraps a segment and all its children. It mounts once and stays mounted while the user navigates between child routes — state inside the layout is preserved. A template does the same structural job, but React gives it a fresh key on every navigation, so it re-mounts and all state resets.

## Root layout requirements

The root layout (`src/app/layout.js`) is the only required layout in an App Router project. It must render the `<html>` and `<body>` tags — no other file does this:

```jsx
// src/app/layout.js
export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
```

Every route in the app renders inside this layout. Fonts, global styles, providers, and persistent chrome (header, footer) all go here.

## Nested layouts

Add a `layout.js` to any sub-folder to wrap just those routes. Layouts compose from the outside in:

```
app/
├── layout.js           ← wraps everything
└── lessons/
    ├── layout.js       ← wraps /lessons and /lessons/[slug]
    └── [slug]/
        └── page.js
```

When a user visits `/lessons/jsx-and-rendering`, the render tree is:

```jsx
<RootLayout>          {/* app/layout.js */}
  <LessonsLayout>     {/* app/lessons/layout.js */}
    <LessonPage />    {/* app/lessons/[slug]/page.js */}
  </LessonsLayout>
</RootLayout>
```

`LessonsLayout` stays mounted as the user moves between lessons — only `LessonPage` swaps out. This is what makes a persistent sidebar feasible: put it in the layout and it never unmounts.

## layout.js vs template.js

| | `layout.js` | `template.js` |
|---|---|---|
| Re-mounts on navigation? | No | Yes (gets a new React key) |
| State preserved? | Yes | No |
| `useEffect` re-fires? | No | Yes |
| Suspense fallback on every nav? | No (only first load) | Yes |

Use `template.js` when you need a clean slate on every navigation — for example, a page-entry animation, a form that should reset when you leave and come back, or a `useEffect` that must re-run on each visit.

## Passing data from params to layouts

When a layout lives inside a dynamic segment, it can read `params` exactly like a page:

```jsx
// src/app/lessons/[slug]/layout.js
export default async function Layout({ children, params }) {
  const { slug } = await params;
  return (
    <section>
      <aside>Sidebar for: {slug}</aside>
      {children}
    </section>
  );
}
```

`params` is a Promise — always `await` it.

## Why searchParams is not available in layouts

`searchParams` (the `?q=...` part of the URL) is not a prop of `layout.js`. This is intentional: layouts are shared across many pages, and making them depend on search params would force every child navigation to re-render the entire layout. Pass `searchParams` down from `page.js` if a layout-level component needs them, or use `useSearchParams()` in a Client Component inside the layout.

<Callout type="warn">
If you try to destructure `searchParams` in a layout, it will be `undefined`. Read search params in `page.js` or in a Client Component using `useSearchParams()` from `next/navigation`.
</Callout>

## Building the lessons sidebar

This app has a nested layout at `src/app/lessons/layout.js`. It renders a persistent sidebar showing all chapters and lessons, with the active lesson highlighted. On mobile it collapses to a dropdown.

The layout file is a Server Component that fetches the lesson data and passes it to a Client Component for the interactive parts (active-link detection via `usePathname`):

```jsx
// src/app/lessons/layout.js
import { getLessonsByChapter } from '@/lib/lessons';
import { LessonSidebar } from '@/components/LessonSidebar';

export default function LessonsLayout({ children }) {
  const chapters = getLessonsByChapter();
  return (
    <div className="mx-auto max-w-7xl px-4 py-8 lg:flex lg:gap-8">
      <LessonSidebar chapters={chapters} />
      <div className="min-w-0 flex-1">{children}</div>
    </div>
  );
}
```

`LessonSidebar` is a `'use client'` component that uses `usePathname()` to highlight the current lesson. On desktop it renders an `<aside>`; on mobile it renders a `<select>` that navigates on change.

## Key takeaways

<Callout type="tip">
**Layouts persist, pages swap.** When the user navigates between child routes, the layout stays mounted and only the `page.js` component re-renders. Use this for sidebars, headers, and any persistent UI.

**Root layout is required and owns `<html>` and `<body>`.** Nothing else in the app can render these tags.

**Nest layouts for scoped chrome.** A layout in `lessons/` applies only to `/lessons/*` — it does not affect the home page or any other route outside that folder.

**`searchParams` lives in pages, not layouts.** Layouts do not receive search params. Read them in `page.js` or with `useSearchParams()` in a Client Component.

**`template.js` for a clean slate.** When you need state to reset on every navigation (entry animations, resetting forms), `template.js` does that — `layout.js` won't.
</Callout>
