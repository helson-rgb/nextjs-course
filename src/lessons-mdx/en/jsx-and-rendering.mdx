# JSX & Rendering

JSX is a syntax extension that lets you write markup inside JavaScript files. It looks like HTML — but it is not HTML. Under the hood, every JSX expression compiles to a plain `React.createElement()` call before the browser ever runs your code.

## What JSX compiles to

The Next.js compiler transforms your JSX at build time. This JSX:

```jsx
const el = <h1 className="title">Hello world</h1>;
```

Is identical at runtime to this JavaScript:

```js
const el = React.createElement('h1', { className: 'title' }, 'Hello world');
```

`React.createElement(type, props, ...children)` returns a plain JavaScript object — a **React element** — that describes what should appear on screen. You never write it by hand; JSX is the shorthand that makes it readable.

Nesting works the same way:

```jsx
// What you write:
const card = (
  <div className="card">
    <h2>Title</h2>
    <p>Body.</p>
  </div>
);

// What the compiler produces:
const card = React.createElement(
  'div',
  { className: 'card' },
  React.createElement('h2', null, 'Title'),
  React.createElement('p', null, 'Body.')
);
```

Each level of nesting becomes a nested `React.createElement` call. The resulting tree of objects is the **virtual DOM**.

## Expressions, attributes, and fragments

### Embedding expressions

Wrap any JavaScript **expression** in `{}` to embed it inside markup:

```jsx
const user = { name: 'Alice', score: 42 };

return (
  <p>
    {user.name} scored {user.score} points.
  </p>
);
```

The value inside `{}` can be a string, number, array, or any expression that produces a value. **Statements** — `if`, `for`, `while` — do not produce values. Use a ternary or `&&` instead:

```jsx
// ternary: one branch or the other
{isLoggedIn ? <Dashboard /> : <Login />}

// short-circuit: render only when true
{hasError && <ErrorBanner message={error.message} />}
```

### Attribute differences

JSX attributes follow JavaScript naming rules, not HTML rules. The two differences you will encounter in every project:

| HTML | JSX | Reason |
|---|---|---|
| `class="btn"` | `className="btn"` | `class` is a JS reserved word |
| `for="email"` | `htmlFor="email"` | `for` is a JS reserved word |
| `<br>` | `<br />` | Every tag must close |
| `<input>` | `<input />` | Every tag must close |

All other common attributes — `id`, `href`, `src`, `style`, `aria-*`, `data-*` — are spelled identically to HTML.

<Callout type="warn">
Passing `class` instead of `className` does not throw an error in JSX — it silently writes the wrong attribute to the DOM, no CSS is applied, and the bug can be invisible until you open DevTools. Playground 2 below will show you this first-hand.
</Callout>

### Self-closing tags

In JSX, **every tag must close** — either with a matching closing tag or a self-closing slash before the `>`:

```jsx
<img src="/logo.svg" alt="Next Academy" />
<input type="email" name="email" />
<hr />
<br />
```

### Fragments and the single-root rule

A component can only return **one root element**. This fails:

```jsx
// SyntaxError: Adjacent JSX elements must be wrapped in an enclosing tag.
return (
  <h1>Title</h1>
  <p>Subtitle</p>
);
```

The obvious fix is a wrapper `<div>` — but that adds a meaningless node to the DOM and can break layouts (especially in tables and flex/grid containers). **Fragments** group elements without adding anything to the real DOM:

```jsx
return (
  <>
    <h1>Title</h1>
    <p>Subtitle</p>
  </>
);
```

`<>...</>` is shorthand for `<React.Fragment>...</React.Fragment>`. Use the named form when you need to pass a `key` prop (e.g. inside a `.map()`):

```jsx
items.map((item) => (
  <React.Fragment key={item.id}>
    <dt>{item.term}</dt>
    <dd>{item.definition}</dd>
  </React.Fragment>
));
```

## From JSX to real DOM

When your component returns JSX, React builds a **virtual DOM** — a lightweight tree of plain JavaScript objects that mirrors the shape of the UI you described.

On the first render, React converts this tree into real DOM nodes. On every subsequent render, it **diffs** the new virtual tree against the previous one and applies only the minimal set of changes — a process called **reconciliation**.

```
Your JSX
  ↓ compiler
React.createElement calls
  ↓ render
Virtual DOM object tree
  ↓ reconciliation diff
Minimal real DOM patches
```

You never call `document.createElement` directly. You describe the UI you want; React figures out the cheapest sequence of DOM operations to match it.

<Callout type="info">
The full reconciliation algorithm — including how React decides when to reuse vs. destroy a DOM node — is covered in Lesson 4, where stable `key` props become critical. For now the mental model is: React keeps a fast in-memory copy and syncs the real DOM as cheaply as possible.
</Callout>

## Key takeaways

<Callout type="tip">
**JSX is syntactic sugar for `React.createElement`.** Every angle-bracket expression compiles to a plain function call that returns a JavaScript object. Understanding this makes JSX errors obvious and debugging straightforward.

**Three attribute rules:** `className` not `class`, `htmlFor` not `for`, and every tag must close with `/>` or a matching closing tag. These produce silent failures — not errors — which makes them easy to miss.

**One root, always — use Fragments.** `<>...</>` groups siblings without adding DOM nodes. It is essential in tables, lists, and flex/grid containers where an extra `<div>` wrapper breaks the layout.

**You describe; React decides.** The virtual DOM and reconciliation algorithm apply only the necessary DOM patches. You never touch `document` directly — that is the abstraction JSX and React give you.
</Callout>
