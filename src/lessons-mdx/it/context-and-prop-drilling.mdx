# Hook Personalizzati, useReducer e Context

Questa lezione è il punto culminante del capitolo sui fondamentali di React. Gli hook personalizzati, `useReducer` e Context sono i tre strumenti che ti permettono di domare la complessità man mano che un'app React cresce: estrai la logica ripetuta, modella le transizioni di state in modo esplicito e condividi i dati senza passare props attraverso ogni livello dell'albero.

## Estrarre la logica in hook personalizzati

Un hook personalizzato è una funzione JavaScript il cui nome inizia con `use` e che chiama almeno un altro hook al suo interno. Tutto qui — nessuna API speciale, nessuna registrazione. Lo scrivi, lo chiami, React lo tratta come qualsiasi altra chiamata a un hook.

```jsx
// useToggle — stato booleano con una funzione flip stabile
import { useState, useCallback } from 'react';

export function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);
  return [on, toggle];
}

// Utilizzo — stesso comportamento di stato, zero boilerplate
const [menuOpen, toggleMenu] = useToggle();
const [isDark, toggleDark] = useToggle();
```

Ogni componente che chiama `useToggle` ottiene il proprio state indipendente — gli hook non sono istanze condivise. Il valore dell'estrazione è riutilizzare la *logica*, non condividere lo *state*.

### useLocalStorage

Persistere lo state in `localStorage` richiede un inizializzatore che legga dallo storage e un effect che scriva. Estrailo una volta sola:

```jsx
import { useState, useEffect } from 'react';

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    // inizializzatore lazy — viene eseguito una sola volta al mount
    try {
      const stored = window.localStorage.getItem(key);
      return stored !== null ? JSON.parse(stored) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {}
  }, [key, value]);

  return [value, setValue];
}
```

Sostituto diretto di `useState`:

```jsx
// Prima
const [theme, setTheme] = useState('light');

// Dopo — persiste tra i ricaricamenti della pagina
const [theme, setTheme] = useLocalStorage('theme', 'light');
```

### useDebounce

Gli input di ricerca che inviano una richiesta di rete a ogni pressione di tasto sono inefficienti. `useDebounce` ritarda l'aggiornamento di un valore finché l'utente non si ferma:

```jsx
import { useState, useEffect } from 'react';

export function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // annulla se il valore cambia prima del delay
  }, [value, delay]);

  return debounced;
}

// Utilizzo
const query = useDebounce(inputValue, 400); // si aggiorna solo dopo 400ms di pausa
useEffect(() => {
  if (query) fetchResults(query);
}, [query]);
```

La funzione di cleanup annulla il timeout in sospeso a ogni pressione di tasto — si attiva solo l'ultima, dopo che l'utente smette di digitare.

### Regole all'interno degli hook personalizzati

Gli hook personalizzati seguono le stesse regole degli hook normali: chiamali al livello superiore, mai all'interno di condizioni o cicli. Poiché gli hook personalizzati chiamano a loro volta degli hook, la garanzia sull'ordine delle chiamate di React si applica a tutto ciò che contengono.

## Quando useReducer supera useState

`useReducer` prende una funzione reducer e uno state iniziale, restituisce lo state corrente e una funzione `dispatch`:

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
dispatch({ type: 'ADD', payload: newItem });
```

Il reducer è una funzione pura: `(currentState, action) => nextState`. Vive fuori dal componente, accetta qualsiasi oggetto action e restituisce un nuovo state.

**Scegli `useReducer` quando:**

- Più chiamate a `useState` si aggiornano sempre insieme (un form con 5 campi).
- Lo state successivo dipende da condizioni complesse che coinvolgono più campi esistenti.
- Vuoi testare le transizioni di state in isolamento — il reducer è una funzione pura, facilmente testabile con unit test.
- Lo stesso state viene modificato da molti eventi diversi e vuoi un unico posto in cui vedere tutte le transizioni.

Confronta la stessa lista di todo espressa in due modi:

```jsx
// useState — disperso, difficile vedere tutte le transizioni in una volta
const [todos, setTodos] = useState([]);
const [filter, setFilter] = useState('all');

function addTodo(text)  { setTodos(prev => [...prev, { id: Date.now(), text, done: false }]); }
function toggleTodo(id) { setTodos(prev => prev.map(t => t.id === id ? {...t, done: !t.done} : t)); }
function removeTodo(id) { setTodos(prev => prev.filter(t => t.id !== id)); }
function clearDone()    { setTodos(prev => prev.filter(t => !t.done)); }
```

```jsx
// useReducer — tutte le transizioni in un posto, con nome ed esplicite
function todosReducer(state, action) {
  switch (action.type) {
    case 'add':
      return [...state, { id: Date.now(), text: action.text, done: false }];
    case 'toggle':
      return state.map(t => t.id === action.id ? { ...t, done: !t.done } : t);
    case 'remove':
      return state.filter(t => t.id !== action.id);
    case 'clear_done':
      return state.filter(t => !t.done);
    default:
      throw new Error('Unknown action: ' + action.type);
  }
}

const [todos, dispatch] = useReducer(todosReducer, []);
dispatch({ type: 'add', text: 'Comprare il latte' });
dispatch({ type: 'toggle', id: 3 });
```

Il `default: throw` è intenzionale — le action sconosciute sono errori del programmatore, non condizioni di runtime.

## Context: state condiviso senza prop drilling

Il prop drilling — passare lo stesso valore attraverso 4 componenti intermedi che non lo usano — è un segnale che il context potrebbe essere d'aiuto:

```jsx
// Passare theme attraverso ogni livello
<App theme={theme}>
  <Layout theme={theme}>
    <Sidebar theme={theme}>
      <Button theme={theme} /> {/* finalmente usato qui */}
    </Sidebar>
  </Layout>
</App>
```

Il Context fornisce un valore in qualsiasi punto dell'albero e lo rende disponibile a qualsiasi discendente che lo richieda — senza props:

```jsx
import { createContext, useContext, useState } from 'react';

// 1. Crea il context — null è il valore sentinella per "provider mancante"
const ThemeContext = createContext(null);

// 2. Il provider possiede lo state e lo distribuisce
export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

// 3. Un hook personalizzato valida il context ed espone un'API pulita
export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (!ctx) throw new Error('useTheme must be used inside <ThemeProvider>');
  return ctx;
}
```

Qualsiasi componente all'interno di `<ThemeProvider>` può chiamare `useTheme()` — a qualsiasi profondità:

```jsx
function Button() {
  const { theme } = useTheme(); // legge dal context
  return <button className={'btn btn--' + theme}>Click</button>;
}
```

<Callout type="warn">
**Il Context ri-renderizza ogni consumer ad ogni cambio di valore.** Quando lo state di `ThemeProvider` si aggiorna, React ri-renderizza *ogni* componente che ha chiamato `useContext(ThemeContext)` — anche se usa solo un campo che non è cambiato. Va bene per dati che cambiano raramente (tema, lingua, utente corrente). È lo strumento sbagliato per state ad alta frequenza (posizione, offset di scroll, un ticker in tempo reale) — usa una libreria di state dedicata come Zustand o Jotai per quelli.

Il Context è un *meccanismo di distribuzione*, non una libreria di gestione dello state. Risolve il prop drilling; non sostituisce Redux.
</Callout>

**Quando il context è lo strumento giusto:**
- Lingua/locale dell'app (cambia al massimo una volta per sessione).
- Tema (chiaro/scuro).
- Utente autenticato (cambia solo al login/logout).
- Impostazioni globali dell'app che si aggiornano raramente.

**Quando non lo è:**
- State condiviso da soli 2–3 componenti adiacenti — solleva lo state al genitore comune più vicino.
- Dati derivati che si aggiornano frequentemente — la composizione di componenti con `children` spesso risolve il prop drilling senza alcun context.

## Punti chiave

<Callout type="tip">
**Un hook personalizzato è solo una funzione che chiama hook.** Chiamalo `use*`, estrai state, effect e logica dal tuo componente, restituisci ciò di cui il chiamante ha bisogno. Ogni componente che chiama l'hook ottiene il proprio state indipendente.

**`useLocalStorage` è `useState` con persistenza.** L'inizializzatore lazy legge dallo storage una volta; l'effect riscrive ad ogni cambio. È un sostituto diretto: `const [x, setX] = useLocalStorage('key', default)`.

**`useReducer` centralizza tutte le transizioni.** Quando un componente ha molti modi di aggiornare lo stesso state, raccoglili in un reducer. Il reducer è puro, testabile e leggibile — ogni transizione è visibile in un unico `switch`.

**Il Context distribuisce; non gestisce.** Usalo per valori condivisi che cambiano raramente (tema, lingua, utente). Ogni cambio di valore del context ri-renderizza tutti i consumer — mantieni i valori del context stabili e preferisci dividere i context per frequenza di aggiornamento.

**Incapsula sempre `useContext` in un hook personalizzato con un null guard.** `if (!ctx) throw new Error(...)` intercetta i componenti renderizzati accidentalmente fuori dal loro provider — un errore a runtime è molto più facile da debuggare di un silenzioso `undefined`.
</Callout>
