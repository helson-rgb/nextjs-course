# Server vs Client Components

Questo è il cambiamento concettuale più importante nell'App Router di Next.js. Ogni componente che scrivi è un Server Component o un Client Component, e la distinzione cambia dove viene eseguito, cosa può fare e quanto JavaScript viene inviato al browser.

## I componenti sono Server per impostazione predefinita

Nell'App Router, ogni componente è un Server Component a meno che tu non dica diversamente. I Server Components vengono eseguiti sul server durante la richiesta (o al build time per le pagine statiche). Vengono renderizzati in HTML e in un formato serializzato leggero chiamato RSC Payload — **nessun JavaScript per loro viene mai inviato al browser**.

```jsx
// src/app/page.js — Server Component (nessuna direttiva necessaria)
export default async function HomePage() {
  const data = await fetch('https://api.example.com/stats');  // viene eseguito sul server
  const stats = await data.json();
  return <h1>Utenti totali: {stats.count}</h1>;
}
```

L'`async/await` qui non è un trucco — è una funzione asincrona standard. Il server la attende prima di inviare l'HTML al client.

## La direttiva 'use client'

`'use client'` è un letterale stringa in cima a un file. Dice a Next.js (e a React) che questo file — e ogni componente importato da esso — viene eseguito nel browser:

```jsx
'use client';

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

`'use client'` disegna un **confine**, non un marcatore "solo questo file". Tutto ciò che viene importato al di sotto di esso — componenti, utility, pacchetti di terze parti — diventa parte del bundle client. Il confine si propaga verso il basso attraverso l'albero delle importazioni.

<Callout type="warn">
`'use client'` non significa "questo componente viene eseguito solo nel browser". Significa "questo file è la radice di un sottoalbero client". Qualsiasi componente importato all'interno di un file `'use client'` è anch'esso un Client Component, anche se non ha la direttiva.
</Callout>

## Cosa viene eseguito dove

Le capacità di ciascun ambiente sono fondamentalmente diverse:

| Capacità | Server Component | Client Component |
|---|---|---|
| `async/await` al livello superiore | ✅ | ❌ (usa `useEffect`) |
| Accesso diretto a database/filesystem | ✅ | ❌ |
| Usare segreti d'ambiente (`process.env`) | ✅ | ❌ (esposto al browser) |
| `useState`, `useReducer` | ❌ | ✅ |
| `useEffect`, `useRef` | ❌ | ✅ |
| API del browser (`window`, `document`, `localStorage`) | ❌ | ✅ |
| Handler degli eventi (`onClick`, `onChange`) | ❌ | ✅ |
| Invia JavaScript al browser | ❌ (nessuno) | ✅ |

Il vantaggio zero-JS è reale. Una pagina con un elenco di prodotti, un articolo markdown o un grafico dashboard che non richiede mai interattività può essere renderizzata come puro HTML. L'utente non scarica alcun codice di componente React — First Contentful Paint più veloce, bundle più piccolo, idratazione meno costosa.

## Il pattern di interleaving

Un Client Component non può importare un Server Component — farlo trascinerebbe codice solo-server nel bundle client. Ma un Server Component può passare un altro Server Component a un Client Component tramite la prop `children`:

```jsx
// ✅ Pattern: il server passa il server come children al client
// src/app/page.js (server)
import { ThemeProvider } from '@/components/ThemeProvider'; // 'use client'
import { Article } from '@/components/Article';             // server

export default function Page() {
  return (
    <ThemeProvider>
      <Article />   {/* renderizzato dal server, passato come children pre-renderizzati */}
    </ThemeProvider>
  );
}
```

`ThemeProvider` riceve `children` come RSC Payload già renderizzato — non importa mai `Article` direttamente, quindi `Article` rimane sul server.

## Albero decisionale

```
Ho bisogno di onClick, onChange o qualsiasi handler di eventi?
  → Client Component

Ho bisogno di useState, useReducer o useContext?
  → Client Component

Ho bisogno di useEffect o useRef?
  → Client Component

Ho bisogno di API del browser (window, document, localStorage)?
  → Client Component

Altrimenti:
  → Server Component (recupera dati, accede al DB, usa segreti)
```

In caso di dubbio, inizia con un Server Component. Aggiungi `'use client'` solo quando incontri uno dei blocchi sopra. Mantieni il confine il più in profondità possibile nell'albero per massimizzare la porzione renderizzata lato server, senza JS.

## Playground 1 — Fetch server → filtro client

Il componente server recupera una lista di post da un endpoint JSON e la passa come prop a un componente client che gestisce l'input del filtro. La logica del filtro richiede `useState`, quindi deve essere un Client Component — ma il data fetching rimane sul server.

<Playground
  template="nextjs"
  files={{
    'app/page.js': `import { PostList } from './PostList';

async function getPosts() {
  const res = await fetch('https://jsonplaceholder.typicode.com/posts?_limit=10');
  return res.json();
}

export default async function Page() {
  const posts = await getPosts();
  return (
    <div style={{ fontFamily: 'sans-serif', padding: '2rem', maxWidth: '600px' }}>
      <h1 style={{ fontSize: '1.5rem', fontWeight: 700, marginBottom: '1.5rem' }}>Posts</h1>
      {/* Passa i dati recuperati dal server al componente client */}
      <PostList posts={posts} />
    </div>
  );
}`,
    'app/PostList.js': `'use client';

import { useState } from 'react';

export function PostList({ posts }) {
  const [query, setQuery] = useState('');
  const filtered = posts.filter(p =>
    p.title.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Filter posts…"
        style={{
          width: '100%', padding: '0.5rem 0.75rem',
          border: '1px solid #e2e8f0', borderRadius: '6px',
          fontSize: '0.875rem', fontFamily: 'sans-serif',
          marginBottom: '1rem', boxSizing: 'border-box',
        }}
      />
      {filtered.length === 0 && (
        <p style={{ color: '#94a3b8', fontSize: '0.875rem' }}>No posts match.</p>
      )}
      <ul style={{ listStyle: 'none', padding: 0, margin: 0, display: 'flex', flexDirection: 'column', gap: '0.5rem' }}>
        {filtered.map(post => (
          <li key={post.id} style={{
            padding: '0.625rem 0.875rem',
            border: '1px solid #e2e8f0',
            borderRadius: '6px',
            fontSize: '0.875rem',
          }}>
            <span style={{ color: '#94a3b8', marginRight: '0.5rem', fontSize: '0.75rem' }}>#{post.id}</span>
            {post.title}
          </li>
        ))}
      </ul>
    </div>
  );
}`,
  }}

## Punti chiave

<Callout type="tip">
**Server per impostazione predefinita — aggiungi `'use client'` solo quando ne hai bisogno.** Ogni componente inizia come Server Component. Aggiungi la direttiva solo quando incontri un blocco rigido: state, effect, API del browser o handler di eventi.

**`'use client'` è un confine, non un interruttore per file.** Tutto ciò che viene importato al di sotto del confine diventa parte del bundle client — inclusi i pacchetti di terze parti. Mantieni il confine il più in profondità possibile nell'albero.

**I Server Components non inviano JS.** Una pagina piena di Server Components viene renderizzata in HTML senza codice React per quei componenti nel bundle. Questo migliora direttamente il tempo di caricamento e il FCP.

**Usa il pattern children per mantenere i server in un albero client.** Un Client Component non può importare un Server Component, ma può riceverne uno come `children` o come prop. Il Server Component viene pre-renderizzato sul server e il Client Component non lo importa mai.

**Albero decisionale: handler di eventi / state / effect / API del browser → client. Tutto il resto → server.**
</Callout>
